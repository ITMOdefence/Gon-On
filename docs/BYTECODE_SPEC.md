# Спецификация байткода Gon&On v1

Этот документ самодостаточен: он не требует чтения исходного кода
компилятора. Он адресован команде, реализующей виртуальную машину (ВМ) на
C/C++, исполняющую байткод, который производит компилятор Gon&On.

Версия формата: **1.0** (соответствует полю `version_major.version_minor` в
заголовке файла, см. ниже). Версия формата и версия языка совпадают в v1, но
концептуально это разные вещи: язык может получить новую версию (v2, v3...),
не меняя мажорную версию формата байткода, если новые языковые конструкции
транслируются в уже существующий набор опкодов.

Документ описывает **строгий профиль 1.0** — тот, который принимают загрузчик и
верификатор GVM. Компилятор не записывает файл, нарушающий хотя бы одно правило
этого документа: перед записью каждый модуль проходит проверку `BytecodeVerifier`
и повторное чтение строгим `BytecodeReader` (см. §7). Общий контракт двух команд,
включая будущий объектный профиль 2.0, лежит в
[`backlog/bytecode-contract.md`](backlog/bytecode-contract.md).

## 1. Модель исполнения

Gon&On v1 компилируется в байткод **стековой машины** — как JVM/Dalvik, не
регистровая архитектура. Каждый вызов функции создаёт кадр (frame), у
которого есть:

- **операндный стек** (operand stack) — временное хранилище значений при
  вычислении выражений;
- **массив локальных переменных (слотов)** фиксированного размера
  `local_count`, индексируемый `0..local_count-1`. Параметры функции
  занимают первые `param_count` слотов **в порядке их объявления** (первый
  параметр — слот 0, второй — слот 1, и так далее). Остальные слоты —
  под `var`/`val` переменные тела функции.

Есть также **call stack** — стек кадров вызовов (обычный стек вызовов
интерпретатора/ВМ, не специфичный для Gon&On).

## 2. Типы значений

Компилятор гарантирует статическую корректность типов внутри байткода —
**ВМ не обязана делать динамическую проверку типов операндов на каждой
операции**, это уже сделано компилятором. Тем не менее, значения на стеке
логически принадлежат одному из типов:

| Тип | Представление |
|---|---|
| `Int` | 32-битное знаковое целое, дополнительный код (`int32_t` в терминах C) |
| `Bool` | логическое значение (true/false) |
| `String` | иммутабельная строка; в constant pool хранится как UTF-8 по контракту libstr (§5.3) |

Как именно ВМ физически представляет значения на стеке (тегированный union,
NaN-boxing, отдельные стеки по типу и т.п.) — целиком её ответственность и
не специфицируется здесь.

**Целочисленное переполнение**: определено как wraparound по модулю 2^32
(поведение как у `int` в Java/Kotlin) — детерминированное, не UB.
**Деление на 0** (`DIV`/`MOD`): runtime-ошибка; конкретный механизм сигнала
об ошибке (trap, код возврата, исключение и т.п.) выбирает ВМ — компилятор
не генерирует проверок на этот случай в байткоде.

## 3. Набор опкодов

Единственный source of truth для нумерации — файл компилятора
`src/main/kotlin/ru/itmo/applang/bytecode/Opcode.kt`. Таблица ниже обязана
ему дословно соответствовать; при расхождении верить коду компилятора и
заводить issue.

Диапазон `0x01`–`0x3F` зарезервирован за v1. Будущие версии языка добавляют
новые опкоды начиная с `0x40`, не меняя семантику существующих кодов v1.

Каждая инструкция кодируется как **1 байт опкода + операнды фиксированного
для этого опкода размера** (переменная общая длина инструкции, но размер
однозначно определяется опкодом — операнд не имеет вариативной длины,
кроме строк в constant pool, которые не являются операндом инструкции).

Обозначение stack effect: `[a, b] -> [c]` означает, что `a` был помещён на
стек **раньше** (лежит глубже), `b` — позже (лежит на вершине), после
выполнения на стеке остаётся один элемент `c`. При pop двух операндов ВМ
обязана трактовать `b` как значение с вершины стека, `a` — как следующее
за ним.

| Код | Мнемоника | Операнды | Stack effect | Семантика |
|---|---|---|---|---|
| `0x01` | `LOAD_CONST` | `idx: u16` | `[] -> [v]` | Кладёт на стек значение `constants[idx]` (тип определяется тегом записи в пуле, см. §5) |
| `0x02` | `LOAD_LOCAL` | `slot: u8` | `[] -> [v]` | Кладёт на стек значение локального слота `slot` |
| `0x03` | `STORE_LOCAL` | `slot: u8` | `[v] -> []` | Снимает значение со стека, записывает в локальный слот `slot` |
| `0x04` | `ADD` | — | `[a, b] -> [a+b]` | Целочисленное сложение (`Int`) |
| `0x05` | `SUB` | — | `[a, b] -> [a-b]` | Целочисленное вычитание |
| `0x06` | `MUL` | — | `[a, b] -> [a*b]` | Целочисленное умножение |
| `0x07` | `DIV` | — | `[a, b] -> [a/b]` | Целочисленное деление (`a / b`); деление на 0 — runtime-ошибка (см. §2) |
| `0x08` | `MOD` | — | `[a, b] -> [a%b]` | Остаток от деления; деление на 0 — runtime-ошибка |
| `0x09` | `NEG` | — | `[a] -> [-a]` | Унарный минус (`Int`) |
| `0x0A` | `CONCAT` | — | `[a, b] -> [a+b]` | Конкатенация строк (`String + String`); компилятор выбирает `CONCAT` вместо `ADD`, когда статически известно, что оба операнда `String` |
| `0x0B` | `CMP_EQ` | — | `[a, b] -> [a==b]` | Равенство (тип `a`/`b` совпадает — гарантия компилятора) |
| `0x0C` | `CMP_NE` | — | `[a, b] -> [a!=b]` | Неравенство |
| `0x0D` | `CMP_LT` | — | `[a, b] -> [a<b]` | Меньше (`Int`) |
| `0x0E` | `CMP_GT` | — | `[a, b] -> [a>b]` | Больше (`Int`) |
| `0x0F` | `CMP_LE` | — | `[a, b] -> [a<=b]` | Меньше или равно (`Int`) |
| `0x10` | `CMP_GE` | — | `[a, b] -> [a>=b]` | Больше или равно (`Int`) |
| `0x11` | `NOT` | — | `[a] -> [!a]` | Логическое отрицание (`Bool`) |
| `0x12` | `JUMP` | `addr: u32` | `[] -> []` | Безусловный переход на абсолютный byte-offset `addr` внутри code-секции **этой же функции** |
| `0x13` | `JUMP_IF_FALSE` | `addr: u32` | `[cond] -> []` | Снимает `Bool` со стека; если `false` — переходит на `addr` |
| `0x14` | `CALL` | `func_idx: u16` | `[argN..arg1] -> [result?]` | Вызывает функцию `functions[func_idx]`. Аргументы должны быть **уже на стеке в обратном порядке** (последний объявленный аргумент — глубже, первый — на вершине), см. §4. После возврата на стеке результат, если вызываемая функция возвращает через `RETURN`, и ничего, если через `RETURN_VOID` (режим возврата, §7.3) |
| `0x15` | `RETURN` | — | `[v] -> []`* | Возврат из функции со значением `v`; `v` появляется на стеке **вызывающего** кадра как результат `CALL` |
| `0x16` | `RETURN_VOID` | — | `[] -> []` | Возврат из функции без значения (`returnType == Unit`) |
| `0x17` | `PRINT` | — | `[v] -> []` | Печатает `v` в stdout без перевода строки (формат вывода см. §6) |
| `0x18` | `PRINTLN` | — | `[v] -> []` | Печатает `v` в stdout с переводом строки |
| `0x19` | `POP` | — | `[v] -> []` | Отбрасывает значение с вершины стека (используется, когда результат выражения-statement не нужен) |

`*` эффект `RETURN`/`RETURN_VOID` указан относительно кадра **вызываемой**
функции — они не оставляют значений в её собственном операндном стеке
(кадр уничтожается), но кладут результат в стек **вызывающего**.

### 3.1 Важно: нет опкодов AND/OR

В наборе **намеренно нет** отдельных логических опкодов `AND`/`OR`.
Операторы `&&` и `||` языка Gon&On компилируются через `JUMP_IF_FALSE`/
`JUMP` с сохранением **short-circuit**-семантики (правый операнд не
вычисляется, если результат уже определён левым). Если бы `&&`/`||`
компилировались в отдельные опкоды, работающие как обычные бинарные
операции, это сломало бы short-circuit и, как следствие, поведение
программ с побочными эффектами в правом операнде. ВМ не должна ожидать
этих опкодов — они не будут сгенерированы компилятором.

## 4. Соглашение о вызове функций

Компилятор кладёт аргументы вызова на стек **в обратном порядке**:
последний по счёту аргумент вызова кладётся первым (лежит глубже в стеке),
первый аргумент — последним (лежит на вершине). Пример: для вызова
`f(a, b, c)` порядок push: `c`, `b`, `a` (в этом порядке инструкций), после
чего стек сверху вниз выглядит как `[a, b, c, ...]`.

ВМ при обработке `CALL` обязана вытолкнуть (pop) ровно `param_count`
значений и присвоить их слотам параметров **в порядке возрастания слота,
соответствующем порядку pop**:

```
pop() -> param[0]  (это a)
pop() -> param[1]  (это b)
pop() -> param[2]  (это c)
```

Это сделано специально, чтобы у ВМ был простой инвариант "N раз pop подряд
даёт параметры по порядку 0..N-1" без разворота списка на стороне
интерпретатора.

## 5. Формат файла `.albc`

Все многобайтовые целые — **big-endian** (сетевой порядок байт). Это
осознанное решение: явная, платформонезависимая договорённость снимает с
повестки классический межкомандный баг с порядком байт.

```
┌─────────────────────────────────────────────┐
│ Header                                       │
│   magic:               4 bytes = "ALBC"      │
│   version_major:        u16                  │
│   version_minor:        u16                  │
│   flags:                u16   (зарезервировано, = 0 в v1) │
│   entry_function_idx:   u16   (индекс main в function table) │
├─────────────────────────────────────────────┤
│ Constant pool                                │
│   constant_count:       u16                  │
│   repeat constant_count раз:                 │
│     tag:               u8  (1=Int32, 2=Bool, 3=String) │
│     value:                                   │
│       Int32  -> 4 bytes big-endian, дополнительный код │
│       Bool   -> 1 byte (ровно 0 или 1)       │
│       String -> length:u32 + length байт UTF-8 (без null-terminator, §5.3) │
├─────────────────────────────────────────────┤
│ Function table                               │
│   function_count:       u16   (от 1 до 65535) │
│   repeat function_count раз:                 │
│     name_const_idx:    u16 (индекс String-константы с именем функции — для отладки/дампов) │
│     param_count:       u8                    │
│     local_count:       u8  (включая параметры — общее число слотов) │
│     code_offset:       u32 (offset в байтах от начала Code section) │
│     code_length:       u32 (длина кода функции в байтах) │
├─────────────────────────────────────────────┤
│ Code section                                 │
│   code_size:            u32                  │
│   bytes: [code_size]    (код всех функций подряд, в порядке function table; │
│                          функция i начинается по смещению code_offset[i] от начала этой секции) │
└─────────────────────────────────────────────┘
EOF — сразу после последнего байта кода
```

Правила раскладки, которые проверяют и компилятор, и строгий reader:

- `flags` равен 0; любое другое значение — отказ, а не «игнорируемые биты».
- Таблица функций не пуста; `entry_function_idx < function_count`.
- `name_const_idx` каждой функции ссылается на существующую `String`-константу.
- `param_count <= local_count`; `code_length > 0`.
- Код функций лежит подряд: первый `code_offset = 0`, каждый следующий равен
  концу предыдущей функции, конец последней равен `code_size`. Разрывов и
  наложений нет.
- После секции кода нет ни одного байта: неизвестный «хвост» — отказ.
- Все `u32` беззнаковые; размеры из файла не принимаются на веру и
  проверяются по оставшимся байтам до выделения памяти.

### 5.1 Версионирование

`version_major`/`version_minor` относятся к **формату байткода**, не к
версии языка напрямую (хотя в v1 они совпадают: `1.0`). Breaking-изменения
формата увеличивают `version_major`. Поддерживается **ровно** версия `1.0`:
файл с другим `version_major` **или** `version_minor` отклоняется, а не
читается «по догадке». Совместимость с будущими minor-версиями не обещается.

### 5.2 Ограничения размеров

| Величина | Поле | Допустимо |
|---|---|---|
| Количество констант | `constant_count: u16` | 0..65535 (после дедупликации, имена функций входят в пул) |
| Количество функций | `function_count: u16` | 1..65535 |
| Индекс константы / функции | `u16` | строго меньше количества; 65535 — невалидный индекс даже при 65535 записях |
| Параметры функции | `param_count: u8` | 0..255, не больше `local_count` |
| Локальные слоты | `local_count: u8` | 0..255, включая параметры |
| Номер слота | `slot: u8` | строго меньше `local_count` |
| Цель перехода | `addr: u32` | начало инструкции своей функции, строго меньше `code_length` |
| Размер кода | `u32` | поле допускает до 4 294 967 295, но компилятор на JVM поддерживает не более 2 147 483 639 байт и явно отклоняет больше |

Значение, не помещающееся в поле, — ошибка компиляции, а не усечение
младших битов. Конкретная GVM может иметь ресурсные пределы строже формата.

### 5.3 Строковые константы (контракт libstr)

Каждая `String`-константа, включая имена функций, — корректный UTF-8 по
RFC 3629, **без байта NUL** внутри текста и **не длиннее 1 048 576 байт**
(`STRING_MAX_LENGTH` библиотеки libstr PUNos). Пустая строка допустима.
Предел считается в байтах UTF-8 после раскрытия escape-последовательностей,
а не в символах исходника. Некорректный UTF-8, NUL и превышение длины — отказ
загрузки; компилятор отклоняет такой литерал ещё на семантической стадии
(`INVALID_STRING_CONSTANT`).

Предел относится к константам файла. Строка, построенная `CONCAT` во время
исполнения, может превысить его — это ошибка времени выполнения GVM, а не
формата.

## 6. Формат вывода `PRINT`/`PRINTLN`

- `Int` — десятичное представление со знаком (например `-5`, `0`, `42`).
- `Bool` — литералы `true`/`false`.
- `String` — как есть, без кавычек и экранирования.

## 7. Контракт компилятора перед ВМ

Компилятор Gon&On не записывает файл, пока модуль не прошёл проверку,
повторяющую правила верификатора GVM (`bytecode/BytecodeVerifier.kt`), а
записанные байты — строгое чтение (`bytecode/BytecodeReader.kt`). Для любого
успешно скомпилированного `.albc` гарантируется следующее.

### 7.1 Структура

Всё из §5: версия `1.0`, `flags = 0`, точный конец файла, непрерывный код,
валидные `entry` и имена функций, строки по контракту libstr, значения в
пределах своих полей.

### 7.2 Все инструкции, включая недостижимые

- Каждый байт кода принадлежит известной инструкции или её операнду;
  операнд не пересекает конец функции.
- Индексы констант, слотов и функций валидны.
- Каждая цель `JUMP`/`JUMP_IF_FALSE` — **начало инструкции** той же функции и
  строго меньше `code_length`. Конец функции — граница, но не цель перехода.
- В одной функции не смешаны `RETURN` и `RETURN_VOID`, даже если один из них
  недостижим.

### 7.3 Режим возврата функции

В файле нет поля типа результата; эффект `CALL` выводится из инструкций
вызываемой функции:

| Режим | Инструкции | Эффект `CALL` |
|---|---|---|
| VALUE | есть `RETURN`, нет `RETURN_VOID` | `h - param_count + 1` |
| VOID | есть `RETURN_VOID`, нет `RETURN` | `h - param_count` |
| NONE | нет инструкций возврата | после `CALL` нет нормального продолжения |

### 7.4 Высоты операндного стека

Анализ идёт по графу управления от первой инструкции с высотой 0
(параметры лежат в слотах, а не на стеке):

- ни одна достижимая инструкция не снимает больше значений, чем есть;
- в точку слияния путей все пути приходят с одинаковой высотой (цикл,
  накапливающий значения, — ошибка);
- `RETURN` выполняется при высоте ровно 1, `RETURN_VOID` — ровно 0;
- ни один достижимый путь не выходит за конец функции без возврата;
- условие `JUMP_IF_FALSE` не вычисляется статически: проверяются обе дуги;
- бесконечный цикл без возврата допустим.

Недостижимым инструкциям высота не назначается — для них действуют только
проверки §7.2.

### 7.5 Что проверка не доказывает

Анализ считает значения, а не их типы: корректность `Int`/`Bool`/`String`
на каждой операции обеспечивает семантический анализ компилятора. Деление
на 0, целочисленное переполнение (поведение определено, см. §2),
переполнение call stack, нехватка памяти и превышение длины строки при
`CONCAT` остаются ответственностью ВМ во время исполнения.

### 7.6 Категории отказа

`BytecodeFormatException` компилятора и reference-reader несёт категорию с
теми же именами, что `BytecodeIssue` верификатора GVM: `TRUNCATED`, `MAGIC`,
`VERSION`, `FLAGS`, `CONSTANT_TAG`, `BOOLEAN`, `STRING`, `LAYOUT`, `ENTRY`,
`FUNCTION_NAME`, `PARAMETERS`, `OPCODE`, `OPERAND`, `CONSTANT_INDEX`,
`LOCAL_INDEX`, `FUNCTION_INDEX`, `JUMP_TARGET`, `STACK_UNDERFLOW`,
`STACK_JOIN`, `RETURN`, `FALLOFF`, `RESOURCE_LIMIT`. Это позволяет
сопоставлять отказы двух реализаций на одном и том же файле.

## 8. Пример: полный байткод `examples/hello_world.al`

Исходник:

```applang
fun main(): Int {
    println("Hello, world!");
    return 0;
}
```

Дизассемблированный вывод (получен `Disassembler` компилятора, доступен как
reference-инструмент для сверки собственного парсера формата — им же
сгенерирован golden-файл `examples/hello_world.albc.asm`):

```
; AppLang bytecode disassembly
; version 1.0

.constants
  0: String "Hello, world!"
  1: Int32 0
  2: String "main"

.function main(params=0, locals=0)  ; entry point
  0000: LOAD_CONST 0
  0003: PRINTLN
  0004: LOAD_CONST 1
  0007: RETURN
```

Более содержательные примеры: `examples/factorial_while.al` (локальные
переменные, `while`, вызов функции с аргументом) и `examples/gcd_demo.al`
(`if/else`, обе ветки которого возвращают значение, — переход после
then-ветки не генерируется). Их golden-дампы `*.albc.asm` можно использовать
как smoke-test для собственного загрузчика `.albc`: если ВМ умеет прочитать
эти файлы и правильно провести трассировку (`factorial_while` печатает `120`,
`gcd_demo` — `12` и `1`), базовый набор опкодов реализован верно.
