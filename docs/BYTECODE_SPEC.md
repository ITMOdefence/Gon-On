# Спецификация байткода AppLang v1

Этот документ самодостаточен: он не требует чтения исходного кода
компилятора. Он адресован команде, реализующей виртуальную машину (ВМ) на
C/C++, исполняющую байткод, который производит компилятор AppLang.

Версия формата: **1.0** (соответствует полю `version_major.version_minor` в
заголовке файла, см. ниже). Версия формата и версия языка совпадают в v1, но
концептуально это разные вещи: язык может получить новую версию (v2, v3...),
не меняя мажорную версию формата байткода, если новые языковые конструкции
транслируются в уже существующий набор опкодов.

## 1. Модель исполнения

AppLang v1 компилируется в байткод **стековой машины** — как JVM/Dalvik, не
регистровая архитектура. Каждый вызов функции создаёт кадр (frame), у
которого есть:

- **операндный стек** (operand stack) — временное хранилище значений при
  вычислении выражений;
- **массив локальных переменных (слотов)** фиксированного размера
  `local_count`, индексируемый `0..local_count-1`. Параметры функции
  занимают первые `param_count` слотов **в порядке их объявления** (первый
  параметр — слот 0, второй — слот 1, и так далее). Остальные слоты —
  под `var`/`val` переменные тела функции.

Есть также **call stack** — стек кадров вызовов (обычный стек вызовов
интерпретатора/ВМ, не специфичный для AppLang).

## 2. Типы значений

Компилятор гарантирует статическую корректность типов внутри байткода —
**ВМ не обязана делать динамическую проверку типов операндов на каждой
операции**, это уже сделано компилятором. Тем не менее, значения на стеке
логически принадлежат одному из типов:

| Тип | Представление |
|---|---|
| `Int` | 32-битное знаковое целое, дополнительный код (`int32_t` в терминах C) |
| `Bool` | логическое значение (true/false) |
| `String` | иммутабельная строка; в constant pool хранится как UTF-8 |

Как именно ВМ физически представляет значения на стеке (тегированный union,
NaN-boxing, отдельные стеки по типу и т.п.) — целиком её ответственность и
не специфицируется здесь.

**Целочисленное переполнение**: определено как wraparound по модулю 2^32
(поведение как у `int` в Java/Kotlin) — детерминированное, не UB.
**Деление на 0** (`DIV`/`MOD`): runtime-ошибка; конкретный механизм сигнала
об ошибке (trap, код возврата, исключение и т.п.) выбирает ВМ — компилятор
не генерирует проверок на этот случай в байткоде.

## 3. Набор опкодов

Единственный source of truth для нумерации — файл компилятора
`src/main/kotlin/ru/itmo/applang/bytecode/Opcode.kt`. Таблица ниже обязана
ему дословно соответствовать; при расхождении верить коду компилятора и
заводить issue.

Диапазон `0x01`–`0x3F` зарезервирован за v1. Будущие версии языка добавляют
новые опкоды начиная с `0x40`, не меняя семантику существующих кодов v1.

Каждая инструкция кодируется как **1 байт опкода + операнды фиксированного
для этого опкода размера** (переменная общая длина инструкции, но размер
однозначно определяется опкодом — операнд не имеет вариативной длины,
кроме строк в constant pool, которые не являются операндом инструкции).

Обозначение stack effect: `[a, b] -> [c]` означает, что `a` был помещён на
стек **раньше** (лежит глубже), `b` — позже (лежит на вершине), после
выполнения на стеке остаётся один элемент `c`. При pop двух операндов ВМ
обязана трактовать `b` как значение с вершины стека, `a` — как следующее
за ним.

| Код | Мнемоника | Операнды | Stack effect | Семантика |
|---|---|---|---|---|
| `0x01` | `LOAD_CONST` | `idx: u16` | `[] -> [v]` | Кладёт на стек значение `constants[idx]` (тип определяется тегом записи в пуле, см. §5) |
| `0x02` | `LOAD_LOCAL` | `slot: u8` | `[] -> [v]` | Кладёт на стек значение локального слота `slot` |
| `0x03` | `STORE_LOCAL` | `slot: u8` | `[v] -> []` | Снимает значение со стека, записывает в локальный слот `slot` |
| `0x04` | `ADD` | — | `[a, b] -> [a+b]` | Целочисленное сложение (`Int`) |
| `0x05` | `SUB` | — | `[a, b] -> [a-b]` | Целочисленное вычитание |
| `0x06` | `MUL` | — | `[a, b] -> [a*b]` | Целочисленное умножение |
| `0x07` | `DIV` | — | `[a, b] -> [a/b]` | Целочисленное деление (`a / b`); деление на 0 — runtime-ошибка (см. §2) |
| `0x08` | `MOD` | — | `[a, b] -> [a%b]` | Остаток от деления; деление на 0 — runtime-ошибка |
| `0x09` | `NEG` | — | `[a] -> [-a]` | Унарный минус (`Int`) |
| `0x0A` | `CONCAT` | — | `[a, b] -> [a+b]` | Конкатенация строк (`String + String`); компилятор выбирает `CONCAT` вместо `ADD`, когда статически известно, что оба операнда `String` |
| `0x0B` | `CMP_EQ` | — | `[a, b] -> [a==b]` | Равенство (тип `a`/`b` совпадает — гарантия компилятора) |
| `0x0C` | `CMP_NE` | — | `[a, b] -> [a!=b]` | Неравенство |
| `0x0D` | `CMP_LT` | — | `[a, b] -> [a<b]` | Меньше (`Int`) |
| `0x0E` | `CMP_GT` | — | `[a, b] -> [a>b]` | Больше (`Int`) |
| `0x0F` | `CMP_LE` | — | `[a, b] -> [a<=b]` | Меньше или равно (`Int`) |
| `0x10` | `CMP_GE` | — | `[a, b] -> [a>=b]` | Больше или равно (`Int`) |
| `0x11` | `NOT` | — | `[a] -> [!a]` | Логическое отрицание (`Bool`) |
| `0x12` | `JUMP` | `addr: u32` | `[] -> []` | Безусловный переход на абсолютный byte-offset `addr` внутри code-секции **этой же функции** |
| `0x13` | `JUMP_IF_FALSE` | `addr: u32` | `[cond] -> []` | Снимает `Bool` со стека; если `false` — переходит на `addr` |
| `0x14` | `CALL` | `func_idx: u16` | `[argN..arg1] -> [result?]` | Вызывает функцию `functions[func_idx]`. Аргументы должны быть **уже на стеке в обратном порядке** (последний объявленный аргумент — глубже, первый — на вершине), см. §4. После возврата — на стеке результат, если `returnType != Unit`, иначе ничего |
| `0x15` | `RETURN` | — | `[v] -> []`* | Возврат из функции со значением `v`; `v` появляется на стеке **вызывающего** кадра как результат `CALL` |
| `0x16` | `RETURN_VOID` | — | `[] -> []` | Возврат из функции без значения (`returnType == Unit`) |
| `0x17` | `PRINT` | — | `[v] -> []` | Печатает `v` в stdout без перевода строки (формат вывода см. §6) |
| `0x18` | `PRINTLN` | — | `[v] -> []` | Печатает `v` в stdout с переводом строки |
| `0x19` | `POP` | — | `[v] -> []` | Отбрасывает значение с вершины стека (используется, когда результат выражения-statement не нужен) |

`*` эффект `RETURN`/`RETURN_VOID` указан относительно кадра **вызываемой**
функции — они не оставляют значений в её собственном операндном стеке
(кадр уничтожается), но кладут результат в стек **вызывающего**.

### 3.1 Важно: нет опкодов AND/OR

В наборе **намеренно нет** отдельных логических опкодов `AND`/`OR`.
Операторы `&&` и `||` языка AppLang компилируются через `JUMP_IF_FALSE`/
`JUMP` с сохранением **short-circuit**-семантики (правый операнд не
вычисляется, если результат уже определён левым). Если бы `&&`/`||`
компилировались в отдельные опкоды, работающие как обычные бинарные
операции, это сломало бы short-circuit и, как следствие, поведение
программ с побочными эффектами в правом операнде. ВМ не должна ожидать
этих опкодов — они не будут сгенерированы компилятором.

## 4. Соглашение о вызове функций

Компилятор кладёт аргументы вызова на стек **в обратном порядке**:
последний по счёту аргумент вызова кладётся первым (лежит глубже в стеке),
первый аргумент — последним (лежит на вершине). Пример: для вызова
`f(a, b, c)` порядок push: `c`, `b`, `a` (в этом порядке инструкций), после
чего стек сверху вниз выглядит как `[a, b, c, ...]`.

ВМ при обработке `CALL` обязана вытолкнуть (pop) ровно `param_count`
значений и присвоить их слотам параметров **в порядке возрастания слота,
соответствующем порядку pop**:

```
pop() -> param[0]  (это a)
pop() -> param[1]  (это b)
pop() -> param[2]  (это c)
```

Это сделано специально, чтобы у ВМ был простой инвариант "N раз pop подряд
даёт параметры по порядку 0..N-1" без разворота списка на стороне
интерпретатора.

## 5. Формат файла `.albc`

Все многобайтовые целые — **big-endian** (сетевой порядок байт). Это
осознанное решение: явная, платформонезависимая договорённость снимает с
повестки классический межкомандный баг с порядком байт.

```
┌─────────────────────────────────────────────┐
│ Header                                       │
│   magic:               4 bytes = "ALBC"      │
│   version_major:        u16                  │
│   version_minor:        u16                  │
│   flags:                u16   (зарезервировано, = 0 в v1) │
│   entry_function_idx:   u16   (индекс main в function table) │
├─────────────────────────────────────────────┤
│ Constant pool                                │
│   constant_count:       u16                  │
│   repeat constant_count раз:                 │
│     tag:               u8  (1=Int32, 2=Bool, 3=String) │
│     value:                                   │
│       Int32  -> 4 bytes big-endian, дополнительный код │
│       Bool   -> 1 byte (0 или 1)             │
│       String -> length:u32 + length байт UTF-8 (без null-terminator) │
├─────────────────────────────────────────────┤
│ Function table                               │
│   function_count:       u16                  │
│   repeat function_count раз:                 │
│     name_const_idx:    u16 (индекс String-константы с именем функции — для отладки/дампов) │
│     param_count:       u8                    │
│     local_count:       u8  (включая параметры — общее число слотов) │
│     code_offset:       u32 (offset в байтах от начала Code section) │
│     code_length:       u32 (длина кода функции в байтах) │
├─────────────────────────────────────────────┤
│ Code section                                 │
│   code_size:            u32                  │
│   bytes: [code_size]    (код всех функций подряд, в порядке function table; │
│                          функция i начинается по смещению code_offset[i] от начала этой секции) │
└─────────────────────────────────────────────┘
```

### 5.1 Версионирование

`version_major`/`version_minor` относятся к **формату байткода**, не к
версии языка напрямую (хотя в v1 они совпадают: `1.0`). Breaking-изменения
формата увеличивают `version_major`; ВМ обязана **отказываться загружать**
файл с неизвестным (большим, чем поддерживаемый) `version_major`, а не
пытаться угадать layout. Изменения, добавляющие данные без изменения
интерпретации существующих полей, могут увеличивать только
`version_minor`.

### 5.2 Ограничения размеров (v1)

`u16` на число функций и констант, `u8` на `param_count`/`local_count` —
этого с запасом хватает для учебных программ v1, но это ограничение
именно текущей версии формата, а не принципиальный архитектурный потолок.

## 6. Формат вывода `PRINT`/`PRINTLN`

- `Int` — десятичное представление со знаком (например `-5`, `0`, `42`).
- `Bool` — литералы `true`/`false`.
- `String` — как есть, без кавычек и экранирования.

## 7. Контракт компилятора перед ВМ

Компилятор AppLang **гарантирует** для любого успешно скомпилированного
(без диагностик-ошибок) `.albc`-файла:

- операндный стек в любой точке кода каждой функции статически
  сбалансирован — общее число push равно общему числу pop на любом пути
  выполнения от начала функции до соответствующей точки;
- типы операндов на каждой операции корректны (ВМ может не проверять их
  динамически);
- все `addr` в `JUMP`/`JUMP_IF_FALSE` указывают на начало корректной
  инструкции внутри той же функции;
- `func_idx` в `CALL` — валидный индекс в function table, а число значений,
  положенных на стек перед `CALL`, равно `param_count` вызываемой функции.

Что остаётся ответственностью ВМ (runtime, не статически проверяемое
компилятором): деление на 0, целочисленное переполнение (поведение
определено, см. §2, но обнаруживать его — не требуется), переполнение call
stack, нехватка памяти.

## 8. Пример: полный байткод `examples/hello_world.al`

Исходник:

```applang
fun main(): Int {
    println("Hello, world!");
    return 0;
}
```

Дизассемблированный вывод (получен `Disassembler` компилятора, доступен как
reference-инструмент для сверки собственного парсера формата — им же
сгенерирован golden-файл `examples/hello_world.albc.asm`):

```
; AppLang bytecode disassembly
; version 1.0

.constants
  0: String "Hello, world!"
  1: Int32 0
  2: String "main"

.function main(params=0, locals=0)  ; entry point
  0000: LOAD_CONST 0
  0003: PRINTLN
  0004: LOAD_CONST 1
  0007: RETURN
```

Второй, более содержательный пример (локальные переменные, `while`, вызов
функции с аргументом) — `examples/factorial_while.al` и его golden-дамп
`examples/factorial_while.albc.asm`. Оба golden-файла можно использовать как
smoke-test для собственного загрузчика `.albc`: если ВМ умеет прочитать эти
файлы и правильно провести трассировку (для `factorial_while` — напечатать
`120`), базовый набор опкодов реализован верно.
