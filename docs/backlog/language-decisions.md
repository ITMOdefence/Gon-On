# Решения, которые должна определить команда Go&on

Дата: 20 октября 2026 года.  
Область: исходный язык и статическая семантика ООП в рамках принятого контракта 2.0.  
Статус: перечень решений для команды языка; все решения приняты 21 октября 2026 года и зафиксированы в `docs/LANGUAGE_SPEC.md`, раздел 7 (реестр — раздел 14).

## 1. Назначение

Документ перечисляет то, что команда Go&on должна определить самостоятельно, чтобы разработчик мог однозначно написать объектную программу, а компилятор — проверить её и получить предусмотренный байткод.

Это решения об исходном языке и поведении компилятора. Для них не требуется менять внутреннее устройство GVM или согласованный бинарный контракт. Команда выбирает правила, документирует их и проверяет примерами. Если правило уже однозначно установлено действующей спецификацией языка, его нужно сохранить или явно описать изменение; повторно изобретать действующий процедурный базис не требуется.

Наличие пункта не означает требование добавить новую возможность. Допустимое решение — прямо исключить необязательную форму из текущей версии. Существенно, чтобы две похожие программы не получали разный смысл из-за неописанного выбора реализации.

Связанные документы:

- [base.md](base.md) — исправления процедурной совместимости.
- [oop.md](oop.md) — необходимые изменения Go&on для объектной модели GVM.
- [bytecode-contract.md](bytecode-contract.md) — точные байты и правила исполнения 1.0 / 2.0 для обеих команд.

В рамках подготовки этих материалов меняется только бэклог. Исходники и существующие спецификации Go&on вне `docs/backlog` этим документом не изменяются.

## 2. Что уже определено и не является вопросом команды языка

Прежде чем принимать решения ниже, следует учитывать закреплённые ограничения:

| Область | Действующее правило |
| --- | --- |
| Объектное значение | Ссылка на экземпляр конкретного класса; присваивание, аргумент и возврат не копируют поля объекта. |
| Тип поля | Int, Bool, String или конкретный класс; несовместимые классы не преобразуются друг в друга автоматически. |
| Хранение полей | Фиксированные слоты, согласованные с описанием класса; динамического добавления полей нет. |
| Метод | Обычная функция общей таблицы, вызов по индексу через CALL. |
| This | Первый неявный параметр метода и функции инициализации, slot 0; входит в количество параметров и локальных слотов. |
| Получатель метода | Вычисляется первым ровно один раз, затем явные аргументы справа налево. |
| Запись поля | Получатель вычисляется раньше правой части, оба выражения — по одному разу. |
| Создание | Вычисление аргументов справа налево, выделение экземпляра, CALL функции инициализации без результата, затем одна ссылка как результат создания. |
| Незаполненное поле | Служебный NULL не является значением по умолчанию; чтение такого поля — ошибка. |
| Инициализация | Обязательные поля заполнены на всех успешных путях; незаполненное поле нельзя читать, недостроенный this нельзя раскрывать наружу. |
| Отсутствие результата | Внутренний Type.UNIT не является значением, типом переменной или поля. |
| Пределы | Учитываются согласованные ширины, включая this и скрытые временные слоты; способ распределения слотов выбирает компилятор. |

Не следует включать в список свободных языковых решений nullable-поля, неявные подтипы, виртуальный вызов, объектное равенство через существующие CMP_EQ/NE или автоматический вывод OBJ через PRINT. Они не определены текущим контрактом. Их добавление означало бы отдельное расширение, а не заполнение пробела исходного синтаксиса.

Точные номера опкодов, размещение ClassTable, файловые теги и ошибки GVM также не являются предметом этого документа: они уже заданы в bytecode-contract.md.

## 3. Как оформлять каждое решение

Для каждого пункта LANG-01–LANG-10 команда должна записать:

1. Принятое правило без альтернативных трактовок.
2. Допустимые формы записи и ограничения.
3. Не менее одного корректного и одного некорректного примера; для некорректного — причину отказа.
4. Правила разрешения неоднозначностей, если они возможны.
5. Влияние на действующие программы Go&on.
6. Проверяемые условия приёмки.

Для синтаксиса дополнительно нужна грамматика; для семантики — правило проверки, а не только пример. Если форма не поддерживается, это фиксируется прямо. Статус «решено» означает утверждённое правило, а не наличие черновой реализации, которая случайно принимает один вариант.

## 4. LANG-01. Синтаксис классов, полей и методов

### Что определить

- Как записывается объявление класса и где оно допустимо.
- Где объявляются поля: в теле, заголовке либо в нескольких явно различимых формах.
- Как записываются тип и изменяемость поля.
- Как объявляется метод и чем он отличается от функции верхнего уровня в исходнике.
- Как записывается класс без полей или без методов.
- Где обязательны скобки и точки с запятой в новых конструкциях.

Нужно описать точный состав членов класса. Нельзя оставить ситуацию, когда грамматика принимает произвольный оператор в теле класса, а дальнейшая стадия не определяет, когда он должен выполняться.

### Почему это решение Go&on

GVM получает готовые описания классов и код. Ей не важно, написано ли поле в заголовке или теле, если компилятор формирует тот же набор полей и корректную инициализацию.

### Результат

- Фрагмент грамматики объявлений.
- Примеры пустого класса, класса с полями и класса с методами.
- Явные примеры запрещённых членов.
- Правила совместного размещения классов и функций в одной программе.

## 5. LANG-02. Создание экземпляра и запись конструктора

### Что определить

- Как записывается выражение создания: отдельное ключевое слово, специальная форма вызова или другая однозначная конструкция.
- Как объявляется пользовательский конструктор и его параметры.
- Что происходит, если конструктор явно не объявлен: создаётся ли неявная функция инициализации и при каких условиях она допустима.
- Как конструктор класса без явных параметров вызывается из исходника.
- Разрешён ли ранний `return;` в конструкторе и какие проверки ему предшествуют.
- Какие формы конструктора поддержаны в текущем объёме языка; дополнительные формы можно явно исключить.

Если создание выглядит как обычный вызов по имени класса, обязательно определить разрешение конфликта «одно имя может обозначать функцию или класс». Нельзя выбирать трактовку по случайному порядку обхода таблиц символов.

Не требуется вводить перегрузки, делегирование конструкторов, именованные аргументы или значения по умолчанию. Если команда решает поддержать несколько конструкторов уже в текущем объёме, их выбор должен полностью разрешаться компилятором в конкретный индекс функции; нового выбора конструктора внутри GVM не появляется.

### Граница решения

Свобода касается исходной записи и выбора конкретной функции. Протокол исполнения уже принят: выделение отдельно, инициализация обычным CALL с this, результат создания — ссылка, а не результат конструктора. Конструктор не возвращает пользовательское значение.

### Результат

- Грамматика объявления и вызова конструктора.
- Правило выбора функции инициализации.
- Примеры явного / неявного конструктора, если соответствующие формы разрешены.
- Диагностики неподходящих аргументов и запрещённых форм возврата.

## 6. LANG-03. Пространства имён и разрешение обращений

### Что определить

- Могут ли класс и функция верхнего уровня иметь одинаковое имя.
- Могут ли поле и метод одного класса иметь одинаковое имя и как различаются обращения к ним.
- Как разрешается имя, совпадающее у поля, параметра и локальной переменной.
- Разрешено ли обращаться к полю или методу без явного this.
- Что означает вызов без получателя внутри метода: поиск метода, функции верхнего уровня или последовательность этих проверок.
- Как обрабатывается конфликт пользовательского члена со встроенными print / println.
- Как имена классов соотносятся с именами встроенных типов.
- Какие новые слова резервируются грамматикой и где они могут оставаться идентификаторами.

Нужно определить, как новые области имён сочетаются с существующим запретом shadowing локальных переменных. Разрешение имени поля через явный получатель и shadowing локальных переменных — разные вопросы; нельзя автоматически перенести одно правило на другое без описания.

### Уже заданные ограничения

Имена классов уникальны в файле, имена полей уникальны внутри класса. Одинаковые имена членов разных классов разрешаются с учётом конкретного владельца. Список методов содержит разные функции по индексам. Наличие нескольких функций с одинаковым простым именем не обязывает добавлять языковую перегрузку; её поддержка не предполагается молча.

### Результат

Таблица порядка поиска для каждого контекста: имя типа, имя локальной переменной, член с получателем, член без получателя, обычный вызов. Для каждой неоднозначности указать единственный результат или ошибку.

## 7. LANG-04. Типы полей и вывод типов

### Что определить

- Обязателен ли явный тип поля или он может выводиться из инициализатора.
- Если вывод разрешён, какие выражения могут служить основанием и когда он выполняется относительно проверки тел методов.
- Как сообщаются циклические зависимости вывода типов, когда тип одного поля зависит от ещё не определённого другого.
- Как разрешаются ссылки на класс или его члены до текстового объявления.
- Какие действующие правила вывода типа локальной переменной применяются к объектному значению.

К моменту генерации каждое поле обязательно имеет конкретный известный тип. «Пока неизвестный тип» не становится служебным NULL или универсальным объектным типом. Загрузчик не выполняет вывод типов за компилятор.

Если команда выбирает явные типы всех полей, механизм вывода для полей не нужен. Это полноценное решение, которое следует закрепить, а не оставлять неопределённым.

### Результат

- Набор допустимых объявлений.
- Порядок разрешения типов.
- Правила отказа при неоднозначном или циклическом выводе.
- Примеры объектных полей и объектных локальных переменных.

## 8. LANG-05. Инициализаторы полей и порядок выполнения

### Что определить

- Разрешён ли инициализатор непосредственно у объявления поля.
- В каком порядке исполняются такие инициализаторы.
- Когда относительно них выполняется тело конструктора.
- Может ли инициализатор читать другое уже заполненное поле, параметр конструктора или вызывать обычную функцию.
- Какие поля считаются обязательными к заполнению пользователем, а какие получают значение из явно определённого языкового правила.
- Как обрабатывается повторная инициализация поля в объявлении и теле конструктора.

Порядок должен быть выражен точным правилом. Формулировки «инициализировать поля» недостаточно: два инициализатора могут иметь побочные эффекты и читать разные значения.

### Граница совместимости

Служебный NULL не даёт ни одного языкового значения по умолчанию. Если язык явно устанавливает начальное значение какого-либо типа, компилятор обязан сформировать реальное значение и запись через принятый механизм инициализации. Нельзя просто оставить NULL и читать его как готовый Int или объект.

Не требуется, чтобы все поля были параметрами конструктора. Значения могут вычисляться и присваиваться кодом функции инициализации, если соблюдены типы и заполненность.

### Результат

- Единая последовательность выполнения инициализации.
- Пример с наблюдаемым порядком побочных эффектов.
- Пример чтения ранее заполненного поля и отказа при преждевременном чтении.
- Правило для поля без инициализатора и без присваивания в конструкторе.

## 9. LANG-06. Проверка заполненности и ограничение this

### Что уже обязательно

Перед успешным завершением инициализации обязательные поля заполнены на всех путях. Незаполненное поле нельзя читать; недостроенный this нельзя передать наружу. Эти гарантии не выбираются заново. Команда определяет понятные правила исходного языка и способ их статической проверки.

### Что определить

- Какие выражения доступны до полной готовности this.
- Как отдельно учитывается готовность каждого поля и готовность экземпляра в целом.
- Какие действия считаются раскрытием this: аргумент другого вызова, запись во внешний объект, сохранение через другое имя и т. п.
- Как трактуются вызовы методов на this во время инициализации. Правило должно запрещать чтение незаполненного или раскрытие this; разрешать более сложные безопасные случаи необязательно.
- Как анализируются ветвления, циклы, вложенные блоки и ранний возврат.
- Что происходит с полем, которое присваивается только в одной из двух достижимых веток.
- Когда допустимо завершить проверку готовности и разрешить обычное использование экземпляра.

Недостаточно найти в тексте хотя бы одно присваивание полю. Если условие может выбрать ветку без присваивания, поле не гарантировано заполнено. Цикл, который может не выполниться, сам по себе также не доказывает заполненность после цикла.

Компилятор вправе использовать консервативный анализ и отклонять сложные случаи, безопасность которых он не доказывает. Такие ограничения должны быть описаны, чтобы автор программы понимал причину отказа. Нельзя заменить обязательную статическую гарантию надеждой на последующий runtime-отказ GET_FIELD.

### Результат

- Описанная модель состояний заполненности.
- Правила перехода и слияния состояний по управлению.
- Перечень доступных операций с this до и после готовности.
- Примеры с двумя ветками, циклом и ранним возвратом.
- Диагностики незаполненного поля и преждевременного раскрытия this.

## 10. LANG-07. Значение val и var у полей и ссылок

### Что определить

- Как записывается изменяемость поля и каково правило, если модификатор не указан.
- В каких местах разрешено первое присваивание val-полю.
- Считается ли инициализатор объявления уже выполненным первым присваиванием.
- Как проверяется однократность присваивания val на разных путях конструктора.
- Как разрешены последующие записи var после заполнения.
- Как действующие val / var локальных переменных применяются к объектным ссылкам.

Нужно различать три свойства:

1. Можно ли заменить ссылку, хранящуюся в переменной.
2. Можно ли заменить значение конкретного поля объекта.
3. Какие изменения достижимого объекта разрешены через сохранённую ссылку.

Запрет переназначения одной переменной сам по себе не делает все поля экземпляра неизменяемыми. В спецификации следует явно описать это различие на примере двух ссылок на один экземпляр. Глубокая неизменяемость не возникает из наличия слова val и не предполагается как новая обязательная возможность.

### Почему это решение Go&on

В файловом FieldDescriptor нет флага val / var. Компилятор проверяет разрешённость записей и генерирует допустимые GET_FIELD / SET_FIELD. ВМ проверяет класс, тип и границы, но не восстанавливает исходное объявление val из файла.

### Результат

- Правила первой и повторной записи для каждого вида объявления.
- Примеры неизменяемой локальной ссылки на изменяемый объект.
- Примеры поведения alias-ссылок и ветвлений конструктора.
- Диагностика запрещённой записи без обещания отсутствующей runtime-проверки val.

## 11. LANG-08. Видимость и доступность членов

### Что определить

- Из какого кода доступны поля и методы по умолчанию.
- Есть ли в текущем объёме языка разные уровни доступа либо все члены доступны одинаково.
- Если различия доступа есть, как они записываются и как проверяются обращения из другого класса или функции верхнего уровня.
- Как доступность относится к созданию экземпляра и выбору конструктора.

Не требуется вводить private / public или новую модульную систему. Вполне допустимо зафиксировать единый уровень доступа. Но отсутствие решения нельзя подменять тем, что конкретная версия TypeChecker случайно разрешила обращение.

Проверка доступности должна завершаться в компиляторе. В текущем файле нет модификаторов доступа; новая runtime-проверка и новое поле в формате ради этого не требуются. Спецификация не должна обещать защиту private от произвольного чужого байткода, если её обеспечивает только Go&on.

### Результат

- Явная политика доступа для текущего объёма.
- Разрешённые и запрещённые обращения через локальную переменную, параметр и поле другого объекта.
- Понятная диагностика недоступного члена, если такое состояние существует.

## 12. LANG-09. Грамматика выражений и действующий процедурный язык

### Что определить

- Как записываются чтение поля, запись поля и вызов метода.
- Как строятся последовательные обращения через результат предыдущего выражения.
- Как новые постфиксные формы сочетаются со скобками и существующими операторами.
- Является ли присваивание полю только оператором, как текущее локальное присваивание, либо команда явно принимает другое правило.
- Какие синтаксические ошибки должны обнаруживаться сразу: вызов неподходящего члена, недопустимая цель записи, незавершённая цепочка.

Не нужно переопределять уже согласованный порядок выполнения ради новой грамматики: receiver метода вычисляется первым, явные аргументы справа налево; receiver записи — до правой части. Скобки и цепочки не должны приводить к повторному вычислению основания.

Существующие арифметика, сравнения встроенных типов и short-circuit сохраняют свои правила. Метод без результата разрешён как отдельный оператор, но не как значение поля, аргумент или операнд. Объектный результат можно передать, сохранить или вернуть с сохранением его конкретного типа.

### Результат

- Грамматика новых выражений и запись их приоритетов.
- Примеры цепочек с полем-объектом и результатом метода.
- Проверка однократного вычисления получателя с побочным эффектом.
- Примеры сохранения процедурного поведения и корректного отказа для отсутствующего значения.

## 13. LANG-10. Диагностики и исходные приёмочные примеры

### Что определить

- Стабильные коды и содержание ошибок новых языковых правил.
- Какой участок исходника отмечается при ошибке типа, члена, конструктора или заполненности.
- Как сообщается неоднозначное имя, если такая неоднозначность возможна по выбранным правилам.
- Как различаются первичная ошибка и сообщения, являющиеся её следствием.
- Какие исходные программы служат эталонами принятого языка.

Не нужно утверждать точную пунктуацию всех сообщений заранее. Нужно зафиксировать категории, смысл и положение ошибки, чтобы тесты проверяли правило языка и чтобы пользователь не получал внутреннее исключение вместо объяснения.

### Минимальный набор примеров

| Пример | Что он должен подтверждать |
| --- | --- |
| Класс без полей и методов | Допустимая полная запись минимального класса и создания. |
| Класс со скалярным полем | Объявление, тип, инициализация, чтение и разрешённая запись. |
| Поле другого класса | Номинальный тип и корректные цепочки обращений. |
| Две ссылки на экземпляр | Ссылочная семантика и различие val-ссылки / изменяемого поля. |
| Метод с несколькими параметрами | Разрешение имени, receiver-first и обратный порядок аргументов. |
| Конструктор с ветвлением | Заполненность на всех успешных путях. |
| Преждевременное чтение и раскрытие this | Ошибка исходника с понятной позицией. |
| Возврат объекта | Объектный результат функции / метода, сохранение конкретного типа. |
| Функция без результата в выражении | Статический отказ без фиктивного Unit-значения. |
| Программа процедурного базиса | Отсутствие непреднамеренного изменения действующих правил. |

Для корректного примера фиксируются исходник, ожидаемый смысл / результат и существенные элементы понижения. Для неверного — правило и диагностический код. Полные байтовые эталоны берутся из принятого контракта, а не из случайного порядка констант в первой реализации компилятора.

## 15. Что команда может выбрать внутри реализации без изменения контракта

Организация AST, число проходов семантического анализа, внутренние классы символов, размещение разрешённых типов в узлах или отдельных таблицах, алгоритм распределения временных слотов и внутренние имена сгенерированных функций — решения реализации Go&on.

Их можно описывать в техническом плане команды. Они не должны случайно менять наблюдаемую семантику языка, порядок вычислений, пределы формата или байты инструкций. Детерминированный порядок таблиц может выбираться компилятором, если все индексы согласованы и отдельный эталон проверяется по собственному явно заданному порядку.

Не нужно передавать в GVM устройство AST, исходные области видимости или выбор алгоритма проверки заполненности. ВМ получает итоговую программу по уже установленному контракту.
