# Бэклог: изменения Go&on для объектной модели GVM

Дата проверки: 20 октября 2026 года.  
Назначение: требования к команде языка и компилятора.  
Основание: описанная в документации GVM объектная модель и решения пользователя по её сопряжению с Go&on.  
Статус: требования к реализации Go&on; изменения кода не выполнены.

## 1. Цель документа

Определить, что необходимо изменить в Go&on, чтобы его представление классов, объектов, полей, методов и ссылок соответствовало виртуальной машине, описанной документацией GVM.

Документ описывает изменения Go&on под существующую объектную модель GVM и принятые пользователем правила взаимодействия. Архитектура Object / Instance не заменяется. Для объектного файла принят профиль 2.0 при сохранении 1.0 без изменений. Числовые опкоды и точная раскладка теперь закреплены единым контрактом 2.0, воспроизведённым в bytecode-contract.md этого бэклога. Конкретные имена внутренних Kotlin-классов приводятся для объяснения, а не как обязательное устройство реализации.

Команда Go&on получает смысл требований здесь, а точные байты и полный эталон — в [bytecode-contract.md](bytecode-contract.md). Копия этого контракта идентична спецификации в документации GVM. Оставшихся вопросов о раскладке, номерах типов и трёх объектных инструкциях нет; текущий код ещё предстоит реализовать.

## 2. Единый контракт для Go&on и GVM

Существующая модель GVM Object/Instance сохранена. Принятые пользователем семантика выделения, обычный CALL для инициализации, порядок receiver/аргументов, служебный NULL и версия 2.0 дополнены точными байтовыми правилами.

| Область | Закреплённое правило |
| --- | --- |
| Layout 1.0 | Header -> ConstantPool -> FunctionTable -> CodeSection -> EOF, без изменений. |
| Layout 2.0 | Header -> ConstantPool -> FunctionTable -> ClassTable -> CodeSection -> EOF. |
| Header | 12 байт: ALBC, major:u16, minor:u16=0, flags:u16=0, entry:u16. |
| Класс | name_const_idx:u16, field_count:u16, поля по 5 байтов, method_count:u16, function_idx:u16 каждого метода. |
| Тип поля | type_tag:u8 + type_class_idx:u16, всегда 3 байта. 1=Int/2=Bool/3=String с FFFF, 4=OBJ с валидным индексом класса. |
| Выделение | 0x40 ALLOC_OBJECT class_idx:u16, 3 байта; добавляет одну ссылку, не исполняет конструктор. |
| Чтение | 0x41 GET_FIELD class_idx:u16 field_idx:u16, 5 байтов; [receiver]->[value]. |
| Запись | 0x42 SET_FIELD class_idx:u16 field_idx:u16, 5 байтов; [receiver,value]->[]. |
| Метод | Существующий CALL по индексу общей Function; this в slot 0, входит в param_count/local_count. |
| Инициализация | Обычная служебная Function без результата, CALL и RETURN_VOID; отдельного initializer_idx в классе нет. |
| Вычисления | Receiver метода первым один раз, явные аргументы справа налево. Для SET receiver раньше правой части. |
| NULL | Служебная безопасная инициализация, не значение по умолчанию; GET незаполненного поля — ошибка UNINITIALIZED. |

Таблица классов — файловое представление уже описанных Object, а не новая структура вместо них. Имена классов проверяются через индекс String-константы; Object.literal остаётся NULL. Указатели, живые экземпляры и MemoryBlock не сериализуются.

В этой работе изменяются только документация GVM и бэклог Go&on. Код, обычные docs/LANGUAGE_SPEC.md, BYTECODE_SPEC.md, ARCHITECTURE.md и README Go&on не редактируются. Они пока описывают реализованный v1; требования к будущему 2.0 находятся в этом бэклоге.

## 3. Объектная модель, которой должен соответствовать Go&on

### 3.1 Описание класса

В терминологии GVM структура Object хранит описание класса. Это не экземпляр и не набор значений полей конкретного объекта.

Описание включает:

| Сведения | Смысл для компилятора |
| --- | --- |
| objIdx | Идентификатор описания класса. Не является адресом экземпляра или индексом функции. |
| types | Упорядоченные описания полей. Каждая запись содержит имя и объявленный тип. |
| fieldCount | Число полей. |
| funcIdx | Список индексов функций, принадлежащих классу. |
| functionCount | Число таких функций. |

Метаданные классов принадлежат загруженной программе и не меняются при исполнении. Экземпляры ссылаются на эти метаданные. Не нужно создавать новое описание класса при каждом создании экземпляра.

Служебные указатели, дескрипторы MemoryBlock и поля владения GVM не являются данными, которые компилятор должен записать в файл. Назначение поля Object.literal в документации не утверждено; использовать его как готовый договор о хранении имени класса нельзя.

### 3.2 Экземпляр

Структура Instance описывает конкретный экземпляр. Для обычного объекта она содержит ссылку на описание класса и массив значений полей.

Обязательная связь:

```text
описание класса: types[0], types[1], ..., types[N-1]
экземпляр:       data[0],  data[1],  ..., data[N-1]

types[i] задаёт имя и тип значения data[i]
```

Размер массива полей фиксируется при создании и соответствует описанию класса. Разные экземпляры одного класса имеют разные массивы значений, но используют одно описание полей.

### 3.3 Типы значений

GVM различает следующие варианты Value:

| Вариант | Содержимое | Значение для языка |
| --- | --- | --- |
| INT | 32-битное целое непосредственно в Value | Int. |
| BOOL | Логическое значение непосредственно в Value | Bool. |
| STR | Ссылка на строковый экземпляр | String. |
| OBJ | Ссылка на обычный экземпляр с описанием класса | Значение конкретного пользовательского класса. |
| NULL | Безопасное пустое служебное состояние | Само по себе не определяет тип или литерал null языка. |

String имеет отдельный вариант: у строкового экземпляра нет описания пользовательского класса. Нельзя автоматически считать String обычным классом с пользовательскими полями или разрешать операции полей на строке только потому, что она также хранится по ссылке.

Числовые обозначения типов уже присутствуют, но нужно различать три вещи:

| Что обозначается | Определённые значения |
| --- | --- |
| Тег записи константы в .albc 1.0 | 1 = Int32, 2 = Bool, 3 = String. |
| Содержимое Bool-константы | 0 = false, 1 = true; это значение Bool, а не номер его типа. |
| Эскиз C-перечисления ValueType | Порядок NULL, INT, BOOL, STR, OBJ без явных присваиваний даёт в таком объявлении 0, 1, 2, 3, 4. |

Числовые значения и размер C-enum по-прежнему не сериализуются напрямую. Однако теперь общий файловый контракт явно закрепляет теги полей: 1=Int, 2=Bool, 3=String, 4=конкретный класс. У первых трёх следующий u16 равен FFFF, у 4 он равен class_idx. Тег 4 не вводится в ConstantPool; NULL и отсутствие результата не являются типами поля. Существующие константные теги 1/2/3 не меняются.

Общий OBJ-тег в любом случае не отличает Address от Person: для конкретного объектного поля дополнительно нужен идентификатор класса. Внутри GVM ему соответствует ссылка Object*; в файле нужна согласованная числовая ссылка, а не C-адрес.

### 3.4 Тип поля

Описание FieldType хранит тег объявленного типа. Для объектного поля дополнительно указывается конкретное описание класса.

Например, объявленный тип Address означает не просто «какая-нибудь ссылка»: принимается только объект, у которого описание класса совпадает с Address. Два класса с одинаковыми полями не становятся одним типом.

Объявленными типами полей в текущей модели являются Int, Bool, String и конкретный объектный класс. Отсутствие возвращаемого значения функции, обозначаемое внутри Go&on как Type.UNIT, не является типом поля. Служебный NULL также не является объявленным типом поля.

### 3.5 Проверка записи

GVM проверяет номер поля, соответствие значения объявленному типу и принадлежность ссылок приложению. Для объекта требуется точное совпадение конкретного класса. При ошибке прежнее значение поля сохраняется.

Следовательно, компилятор не должен рассчитывать на неявное преобразование Int в Bool, объекта одного класса в другой или пустого служебного значения в значение поля. Эти ошибки нужно обнаруживать при проверке типов исходника там, где они статически известны.

## 4. Изменения типов и таблиц символов Go&on

### 4.1 Что есть сейчас

Типы Go&on заданы закрытым перечислением INT, BOOL, STRING, UNIT. Program хранит только функции. Таблица функций ищет сигнатуру по одному имени. Такая модель не может выразить разные пользовательские классы и владельцев методов.

### 4.2 Что изменить

1. Представлять пользовательский тип как ссылку на конкретный символ класса или его устойчивый идентификатор.
2. Сохранить различие встроенных типов, пользовательских классов и отсутствия результата функции.
3. Добавить учёт описаний классов, их полей, типов полей и принадлежащих классу методов.
4. Разделить идентичность метода и его простое имя: одноимённые методы разных классов должны разрешаться с учётом владельца.
5. Разрешать типы полей, параметров и возвращаемых значений до генерации кода. Не передавать в backend неразрешённое текстовое имя как будто это известный тип.
6. Назначать полям устойчивые номера и сохранять соответствие между таблицей класса и обращениями к полям.
7. При разрешении метода сохранять индекс соответствующей функции общей таблицы и принадлежность классу.

Собирать сведения можно несколькими проходами. Существенен результат: к моменту проверки использования и генерации известны конкретные типы, владельцы и номера, а не поиск по случайному совпадению строк.

### 4.3 Проверки совместимости типов

Для полей обязательна проверка по точному классу, поскольку именно её выполняет GVM. Для параметров и результатов классовые типы также должны сохраняться и проверяться компилятором; отсутствие их полных аннотаций в текущем файле не разрешает смешивать несовместимые значения.

Нельзя считать наследование и неявные преобразования между классами уже поддержанными: в описанном сопоставлении типов нет отношения «потомок подходит вместо родителя». Этот документ не ставит задачу добавить наследование и не требует вносить соответствующие изменения в ВМ.

### 4.4 Критерии готовности

- [ ] Компилятор различает два разных класса с одинаковым набором полей.
- [ ] Объектный тип сохраняется у переменной, поля, параметра, результата и выражения.
- [ ] Несовместимая запись в поле обнаруживается до генерации файла.
- [ ] Разрешённое обращение однозначно связано с описанием класса и его членом.
- [ ] Отсутствие результата и неразрешённый тип не принимаются за объектный тип.

## 5. Изменения грамматики и AST

### 5.1 Необходимые смысловые конструкции

Чтобы выразить описанную объектную модель, Go&on должен представлять:

- объявление пользовательского класса;
- объявление полей с именами и типами;
- принадлежность функции классу, то есть метод;
- получение текущего экземпляра this внутри метода;
- создание экземпляра и его инициализацию;
- чтение поля экземпляра;
- запись поля экземпляра;
- вызов метода с указанием экземпляра.

Сейчас этих конструкций нет в грамматике и AST. В частности, Call хранит только имя глобальной функции, Assign — имя локальной переменной, а type допускает только три встроенных типа.

### 5.2 Требования к представлению

AST должен отличать функцию верхнего уровня от метода с владельцем, локальную переменную от поля экземпляра и обычный вызов от вызова с получателем.

Получатель — выражение, из которого получается нужный экземпляр. Он может быть локальной переменной, полем другого объекта или результатом вызова. Поэтому представления только пары строк «имя переменной + имя поля» недостаточно для общего обращения к объектам.

После семантического анализа обращение к полю должно содержать разрешённый класс, номер поля и тип результата; вызов метода — владельца, разрешённую функцию, параметры и результат. Необязательно хранить эти сведения прямо в каждом AST-узле: допустима отдельная таблица разрешений.

Во всех новых конструкциях сохраняются позиции исходника, чтобы ошибки неизвестного типа, члена или несовместимого значения можно было объяснить до записи файла.

### 5.3 Чего GVM не диктует

Модель GVM не определяет, записывается ли создание как new C(...), C(...) или иначе; где объявлены поля; как выглядит конструктор; обязательны ли явный this и модификаторы доступа.

Этот документ не вводит такие правила. Команда языка должна выразить согласованные конструкции в грамматике, сохраняя перечисленные ниже требования к данным и вызовам. Нельзя выдавать предпочтение одному синтаксису за условие совместимости с GVM.

### 5.4 Критерии готовности

- [ ] AST может представить все перечисленные операции без потери владельца и типа.
- [ ] Пользовательские классы могут использоваться там, где ожидается тип значения.
- [ ] Сложный получатель сохраняется как выражение и не сводится ошибочно к глобальному имени.
- [ ] Синтаксические решения языка не подменяют ещё не описанный бинарный контракт.

## 6. Поля: расположение, чтение и запись

### 6.1 Единое соответствие номеров

Для каждого класса Go&on строит одну последовательность полей и использует её во всех обращениях и метаданных. Если поле address получило номер 1, обращение соответствует data[1] именно этого класса.

Порядок должен быть детерминированным и согласованным с описанием класса. Нельзя отдельно переставить поля в таблице после генерации и оставить прежние номера в инструкциях.

### 6.2 Пример на уровне модели

```text
Класс Person:
  поле 0: age     — Int
  поле 1: address — Address

Экземпляр p класса Person:
  data[0]: Int 30
  data[1]: ссылка на экземпляр Address
```

Чтение address копирует ссылочное Value, а не весь Address. Запись age требует Int, запись address — точный класс Address. Строковый экземпляр не является Person или Address.

### 6.3 Принятые операции полей

Приняты две инструкции с фиксированными кодами и длинами: GET_FIELD=0x41 и SET_FIELD=0x42. Каждая содержит два big-endian u16: class_idx и field_idx, поэтому занимает 5 байтов вместе с опкодом.

| Операция | Операнды инструкции | Стек до | Стек после |
| --- | --- | --- | --- |
| GET_FIELD | Индекс ожидаемого класса, номер поля | `[receiver]` | `[value]` |
| SET_FIELD | Индекс ожидаемого класса, номер поля | `[receiver, value]` | `[]` |

Вершина стека справа, нижележащие значения сохраняются. GET_FIELD сохраняет высоту стека, SET_FIELD уменьшает её на два и ничего не возвращает.

Получатель должен быть экземпляром ожидаемого класса. Номер поля проверяется в этом классе, а не просто в любом экземпляре с достаточно длинным массивом. При записи проверяются объявленный тип значения и принадлежность ссылок приложению. Проверочная ошибка не меняет прежнее значение поля.

Прочитанный служебный NULL не превращается в Int, String или корректную объектную ссылку. Чтение незаполненного поля считается ошибкой; компилятор предотвращает статически обнаруживаемые случаи.

### 6.4 Требования к Go&on

1. Статически разрешить класс получателя, существующее поле, его номер и тип.
2. Проверить точное соответствие записываемого значения типу поля.
3. При чтении вычислить receiver один раз и выдать GET_FIELD с разрешёнными индексами.
4. При записи сначала вычислить receiver один раз, затем правую часть, затем SET_FIELD. Ссылка receiver сохраняется ниже значения на стеке и остаётся доступной GC во время вычисления правой части.
5. Использовать два u16 операнда в указанном порядке и byteSize=5; учесть это в offsets меток, reader, writer, disassembler и verifier.
6. Если язык поддерживает неизменяемые поля, контролировать их изменения в семантическом анализе. В описанном FieldDescriptor GVM нет runtime-флага val; дополнительная структура для него не вводится этим решением.

Пример понижения уже разрешённой записи:

```text
<код receiver>
<код правой части>
SET_FIELD classIndex, fieldIndex
```

Повторный вызов выражения receiver ради доступа к полю запрещён: он может вернуть другой объект или повторить побочный эффект.

### 6.5 Критерии готовности

- [ ] Таблица и инструкции используют согласованную нумерацию полей.
- [ ] GET_FIELD и SET_FIELD имеют принятые операнды и стековые эффекты.
- [ ] Запись вычисляет receiver раньше правой части и не повторяет его.
- [ ] Чтение ссылочного поля сохраняет ссылочную семантику.
- [ ] Несовместимый класс / тип обнаруживается; проверочная ошибка не меняет поле.
- [ ] Кодирование равно 0x41/0x42 + class_idx:u16 + field_idx:u16; длина 5 и big-endian проверены по реальным байтам.

## 7. Методы: существующий вызов по индексу и this

### 7.1 Вызов по индексу уже определён

Метаданные класса содержат funcIdx — индексы функций общей таблицы. Сам код и описание каждой функции находятся в Programm.functions:

```text
Object.funcIdx[k] -> Programm.functions[functionIndex]
```

Вызов конкретного метода выполняется существующим CALL с индексом функции. Go&on разрешает метод по классу получателя и использует этот индекс. Отдельный способ вызова, поиск по строковому имени или новая инструкция CALL_METHOD не нужны.

Индекс в списке методов класса и индекс функции программы не следует путать. Первый служит для выбора записи, второй — операнд CALL. Бинарная запись списка funcIdx закреплена: method_count:u16 и затем function_idx:u16 каждого метода. Код методов остаётся в общей таблице функций. Не включать одну функцию в несколько method lists; у каждого метода param_count>=1.

### 7.2 This и параметры

```text
Метод Counter с двумя явными параметрами:
  slot 0 = this: Counter
  slot 1 = первый явный параметр
  slot 2 = второй явный параметр

param_count = 3
local_count >= 3
```

This включается в оба счётчика; явные параметры сдвигаются на один слот. При сохранении описанных u8-счётчиков param_count и local_count не превышают 255. На явные параметры метода остаётся не более 254, а локальные и скрытые временные слоты дополнительно входят в local_count.

### 7.3 Порядок вычислений и стек перед CALL

Для вызова receiver.method(arg1, arg2) принято:

1. Вычислить receiver ровно один раз и сохранить ссылку во временном локальном слоте.
2. Вычислить явные аргументы справа налево: arg2, затем arg1.
3. Загрузить сохранённый receiver как this.
4. Выполнить CALL с разрешённым индексом метода.

Перед CALL стек снизу вверх:

```text
... argN ... arg2 arg1 this
                         ^ вершина

pop() -> slot 0 = this
pop() -> slot 1 = arg1
pop() -> slot 2 = arg2
```

Символический пример:

```text
<код receiver>
STORE_LOCAL tempReceiver
<код arg2>
<код arg1>
LOAD_LOCAL tempReceiver
CALL methodFunctionIndex
```

Вложенные вызовы не должны затирать ещё нужные временные слоты внешнего вызова. Временные слоты входят в local_count и удерживают ссылку для GC. Снятие receiver со стека после STORE_LOCAL не теряет экземпляр, поскольку ссылка уже находится в локальном слоте.

### 7.4 Кадр и результат

CALL добавляет кадр в тот же контекст исполнения. This и параметры оказываются в локальных слотах; операндный стек нового кадра изначально пуст. Обычный метод не создаёт приложение или независимый контекст.

Объектный результат переносится существующим RETURN как одна ссылка. Для отсутствия результата используется RETURN_VOID. Ненужный результат отдельного вызова снимается POP; после вызова без результата лишний POP запрещён.

Сохраняются базовые проверки: не смешивать RETURN и RETURN_VOID, требовать ровно одно значение на RETURN и ноль на RETURN_VOID, не допускать достижимый выход за конец функции без возврата. This в локальном слоте не добавляется к высоте операндного стека.

### 7.5 Что не добавляется

Существующий вызов по индексу не требует новой таблицы виртуальной диспетчеризации или дополнительной полной сигнатуры в файле. Проверку типов receiver и аргументов выполняет Go&on. Новые runtime-проверки CALL / RETURN сверх описанного контракта самостоятельно не назначаются.

### 7.6 Критерии готовности

- [ ] Метод разрешён в индекс общей таблицы, используется существующий CALL.
- [ ] This занимает slot 0 и учтён в счётчиках.
- [ ] Receiver вычисляется первым ровно один раз, аргументы — справа налево.
- [ ] Подготовленный стек заполняет параметры правильными значениями.
- [ ] Вложенные вызовы не повреждают временные ссылки.
- [ ] Возврат и POP сохраняют корректную высоту стека и ссылочную семантику.

## 8. Ссылочная семантика и время жизни

### 8.1 Присваивание и передача

Присваивание объекта, передача параметром и возврат копируют ссылку на тот же экземпляр. Поля объекта при этом не копируются.

```text
a ссылается на экземпляр X
b получает значение a

a и b ссылаются на один X
изменение поля X через b видно при чтении через a
```

Другой экземпляр с теми же значениями полей остаётся отдельным объектом. Но это само по себе не задаёт результат языкового оператора ==: поддержка равенства объектов рассматривается отдельно в разделе 11.

### 8.2 Время жизни не равно времени жизни кадра

Объект, созданный внутри функции и возвращённый вызывающему, не должен исчезнуть после завершения функции. Go&on не вставляет его ручное освобождение при выходе из блока, RETURN или снятии временной ссылки.

Время жизни определяет достижимость для GC GVM. Не нужны операции увеличения / уменьшения счётчика ссылок, рекурсивное удаление ссылочных полей или копирование объекта в «память родителя».

### 8.3 Где должны сохраняться ссылки

Описанные корни GVM включают значения локальных слотов и операндных стеков живых вызовов, поля достижимых экземпляров, строковые константы и сохраняемые результаты контекстов. Реестр выделений не является корнем.

При генерации Go&on должен сохранять ссылку, которая понадобится после других вычислений, в предусмотренном корневом хранилище. Например, если receiver нужен после вычисления аргументов, нельзя забыть его или считать, что сам факт выделения удерживает экземпляр живым. Конкретное использование стека / локального слота определяется согласованными инструкциями.

Атомарность нативного выделения и защита временных C-указателей внутри интерпретатора относятся к реализации GVM; это не задача добавить новые структуры или команды в компилятор.

### 8.4 Граница приложения

Все объектные и строковые ссылки относятся к одному приложению. Go&on не должен кодировать адрес экземпляра как Int, строку или произвольные байты для передачи в другую программу. Прямой обмен живыми объектными ссылками между приложениями не предусмотрен этой моделью.

### 8.5 Критерии готовности

- [ ] Присваивание / аргумент / возврат не создают неявных копий экземпляра.
- [ ] Возвращённая ссылка остаётся доступной после завершения создавшей её функции.
- [ ] Временные значения не теряются до последнего использования.
- [ ] Генератор не освобождает объекты вручную и не вставляет подсчёт ссылок.
- [ ] Обычный вызов метода не создаёт межприложную передачу ссылок.

## 9. Принятые создание экземпляра и функция инициализации

### 9.1 Отдельная инструкция выделения

Принята инструкция ALLOC_OBJECT=0x40 с class_idx:u16 big-endian. Длина ровно 3 байта, эффект стека +1. Индекс проверяется по class_count перед доступом к Object. Опкоды 0x43 и далее не назначены.

```text
ALLOC_OBJECT classIndex
Стек: [...] -> [..., objectReference]
```

Инструкция создаёт экземпляр нужного класса с количеством полей из существующего описания Object и кладёт одну ссылку на стек. Нижележащие значения сохраняются. Она не принимает значения всех полей и не исполняет пользовательский конструктор.

Полям первоначально присваивается служебный NULL в соответствии с механизмом instance_create_object. Это безопасное внутреннее состояние, а не успешная языковая инициализация. При ошибке выделения успешной ссылки нет; обычная обработка отказа остаётся в GVM.

Go&on не формирует новый Object при каждом ALLOC_OBJECT: инструкция ссылается на ранее загруженное описание класса.

### 9.2 Обычная функция инициализации

Для создания с инициализацией Go&on формирует функцию с обычным индексом общей таблицы:

- неявный параметр this занимает slot 0;
- явные параметры инициализации идут после this;
- param_count включает this;
- функция присваивает начальные значения полям;
- функция не возвращает значения и завершается RETURN_VOID;
- вызов выполняется существующим CALL по её индексу.

Инициализаторы полей включаются в эту функцию вместе с предусмотренным языком кодом конструктора в согласованном порядке. Это не требование объявлять все поля параметрами заголовка класса. Конкретный синтаксис инициализаторов / конструктора данный документ не назначает.

### 9.3 Генерация выражения создания

Принята следующая последовательность:

1. Вычислить аргументы конструктора справа налево, сохраняя действующее правило обычных вызовов Go&on.
2. Выполнить ALLOC_OBJECT для разрешённого класса.
3. Сохранить полученную ссылку во временном локальном слоте. Аргументы остаются ниже в операндном стеке.
4. Загрузить сохранённую ссылку как this на вершину и выполнить CALL функции инициализации.
5. После успешного возврата снова загрузить ссылку из временного слота. Она является единственным результатом выражения создания.

Символический пример для двух явных аргументов:

```text
<код arg2>
<код arg1>
ALLOC_OBJECT classIndex
STORE_LOCAL tempObject
LOAD_LOCAL tempObject
CALL initializerFunctionIndex
LOAD_LOCAL tempObject
```

До CALL стек имеет вид `[... arg2, arg1, this]`. Инициализация снимает параметры, но не оставляет результат. Последний LOAD_LOCAL создаёт результат всего выражения. Без него генератор ошибочно использовал бы отсутствие результата конструктора как объектную ссылку.

Нижележащие значения и вложенные аргументы не должны повреждаться. Временный слот учитывается в local_count и не переиспользуется до последней загрузки.

### 9.4 Заполненность полей и this

Компилятор должен проверять заполнение обязательных полей до успешного завершения инициализации, предотвращать чтение незаполненного поля и передачу недостроенного this наружу. Служебный NULL не преобразуется автоматически в 0, false, пустую строку или допустимую отсутствующую ссылку.

В частности, передача this в другой код, сохранение его во внешнем доступном объекте или вызов метода, который может прочитать незаполненные поля / раскрыть this, не допускаются до доказанной готовности. Прямые инициализирующие записи разрешены по типам полей. Проверка ветвлений должна учитывать все пути успешного возврата, а не только наличие хотя бы одной записи в текстовом теле.

Конкретный алгоритм анализа выбирает команда Go&on; он не должен опираться на неописанную карту инициализации в GVM.

### 9.5 Ошибки и GC

Если вычисление аргумента, выделение или выполнение инициализации завершается ошибкой, выражение создания не выдаёт успешный результат. Последний LOAD_LOCAL не исполняется. Побочные эффекты уже выполненного кода автоматически не откатываются.

Во время исполнения байткода инициализации ссылка удерживается временным слотом вызывающего и слотом this нового кадра. Не нужно запрещать GC на всё время пользовательского конструктора. Его внутренние инструкции выполняются по обычным правилам GVM; обработку освобождения недостижимых / неуспешных объектов выполняет её существующий механизм памяти и GC, а не вставленные компилятором free.

### 9.6 Представление функции инициализации

Инициализатор получает обычный индекс FunctionTable и отладочное String-имя. В ClassTable отдельного initializer_idx нет: Go&on уже знает нужную функцию и записывает её индекс непосредственно в CALL. Инициализатор не добавляется автоматически в список обычных методов. У него this и хотя бы один параметр суммарно, поэтому он не становится entry 2.0 с param_count=0.

### 9.7 Критерии готовности

- [ ] ALLOC_OBJECT получает индекс класса, увеличивает стек на одно значение и не вызывает конструктор.
- [ ] Инициализация — функция общей таблицы с this в slot 0, вызовом CALL и RETURN_VOID.
- [ ] Выражение создания после успеха оставляет одну ссылку, а не отсутствие результата.
- [ ] Аргументы, this и временный слот расположены и учтены правильно.
- [ ] Обязательные поля заполнены на всех успешных путях, преждевременное чтение / раскрытие this отклоняются.
- [ ] Ошибка не публикует успешный результат; ссылки удерживаются для GC без ручного удаления.

## 10. Точная сериализация профиля 2.0

### 10.1 Секции

```text
Header: ALBC + major:u16=2 + minor:u16=0 + flags:u16=0 + entry:u16
ConstantPool: constant_count:u16, прежние константы 1/2/3
FunctionTable: function_count:u16, прежние 12-байтовые записи
ClassTable: class_count:u16, записи классов
CodeSection: code_size:u32, code_bytes[code_size]
EOF
```

Все многобайтовые числа big-endian, padding нет. code_offset отсчитывается от начала code_bytes после поля code_size; таблица классов не входит в offsets функций. После последнего байта кода никакого хвоста.

### 10.2 Записи класса и поля

```text
Class:
  name_const_idx:u16
  field_count:u16
  fields[field_count]:
    name_const_idx:u16
    type_tag:u8
    type_class_idx:u16
  method_count:u16
  function_idx:u16 repeated method_count
```

Индекс класса — позиция записи, индекс поля — позиция в fields. Запись класса занимает 6+5*field_count+2*method_count байтов. Отдельного objIdx в файле нет; name_const_idx указывает на непустую String-константу имени. Имена классов уникальны, имена полей уникальны внутри класса. Имена следуют правилу идентификатора Go&on.

type_tag 1/2/3 обозначает Int/Bool/String с type_class_idx=FFFF. Tag 4 обозначает конкретный класс с индексом меньше class_count. Неверный sentinel, tag=0 или неизвестный tag — ошибка. Все Object создаются стабильно до разрешения ссылок классов, включая прямые / циклические ссылки метаданных.

ClassTable передаёт существующие Object.types/funcIdx. Имя класса нужно для проверки и диагностики, а не для заполнения неутверждённого literal. Имена полей загружаются отдельными владеющими String, дескриптор константы не копируется присваиванием.

### 10.3 Пределы и индексы

class_count, field_count и method_count имеют u16: не более 65535 элементов, последний индекс до 65534. Общие суммы полей всех классов считаются в проверяемом usize / безопасном более широком типе, не усекаются до u16. Общая FunctionTable и ConstantPool также не больше 65535 записей, включая методы, инициализаторы и имена. Счётчики слотов/параметров остаются u8.

Одна функция-метод не принадлежит нескольким классам; method.param_count>=1. Entry 2.0 имеет param_count=0 и не включён в method list. Наличие класса даже без использования выбирает 2.0; профиль 2.0 с class_count=0 допустим. 1.0 сохраняется без объектных секций/инструкций.

Ресурсные настройки GVM могут быть строже разрядностей. Пределы реализации JVM тоже проверяются до усечения / выделения. Новый формат не означает поддержку любого u32-размера массивом JVM.

### 10.4 Инструменты и эталон

Writer, reader, Instruction.byteSize, разрешение меток, disassembler и проверка байткода используют одни и те же 0x40/3, 0x41/5, 0x42/5 и ClassTable. У декодированной GET/SET два самостоятельных индекса. 1.0 отвергает новые команды, 2.0 отвергает неизвестные коды, версии и хвост.

Полная спецификация и проверяемый пример с функцией инициализации находятся в [bytecode-contract.md](bytecode-contract.md). При указанном там порядке констант и функций размер файла 185 байт, code_size=45, entry=2, абсолютное начало code_bytes=140. Это готовый эталон для независимых проверок двух команд, а не фактический прогон текущей GVM.

### 10.5 Критерии готовности

- [ ] Реальные байты соответствуют точной раскладке и не требуют догадок загрузчика.
- [ ] Профиль 1.0 сохранён; 2.0 имеет ClassTable в нужном месте и точный EOF.
- [ ] Теги поля, FFFF и ссылки на классы проверены независимо от C-enum.
- [ ] Длины и операнды трёх инструкций совпадают во всех инструментах.
- [ ] Пример воспроизводится с указанными таблицами / offsets / размерами; корректный код возвращает 7 на реализованной GVM.

## 11. Операции языка, которые нельзя приписывать GVM

### 11.1 Равенство объектов

Документация интерпретатора определяет CMP_EQ / CMP_NE для Int, Bool и String; строки сравниваются по тексту. Равенство объектов и null прямо не вводится этим набором.

Поэтому Go&on нельзя просто расширить проверкой «если оба типа — один класс, сгенерировать существующий CMP_EQ». То, что присваивание копирует ссылку, не является спецификацией оператора равенства. Здесь не назначаются ни сравнение идентичности, ни глубокое сравнение, ни новые инструкции равенства.

### 11.2 Вывод и преобразования

PRINT / PRINTLN описаны для Int, Bool, String. Объектную ссылку нельзя передавать туда как будто ВМ уже имеет автоматическое строковое представление. Ни toString, ни конкатенация объекта со строкой, ни арифметика указателей не являются необходимыми изменениями для совместимости с описанной GVM.

### 11.3 Служебный NULL и nullable

GVM умеет хранить служебный NULL, но её текущее точное сопоставление не принимает его вместо Int, Bool, String или конкретного объектного поля. Поэтому из наличия такого тега не следует поддержка nullable-типа или литерала null в Go&on.

Пользователь подтвердил: служебный NULL остаётся внутренним состоянием, без автоматических значений по умолчанию. Чтение незаполненного поля является ошибкой; статически известные случаи предотвращает компилятор. Nullable-типы этим решением не вводятся и не требуются для начальной стыковки объектов.

### 11.4 Наследование, виртуальность и изменяемость

В описании объекта есть список методов, но нет утверждённой схемы наследования, таблицы виртуальной диспетчеризации или проверки подтипов. Наличие списка функций само по себе не создаёт эти возможности.

В FieldDescriptor есть имя и тип, но нет runtime-флага val, модификатора доступа или accessor. Если такие правила есть в языке, их нужно соблюдать на стороне компилятора, не обещая неописанных проверок ВМ. Добавление этих возможностей не является задачей данного бэклога.

## 12. Решения по формату закрыты; ограничения области

Вопросы, блокировавшие точную генерацию объектов, закрыты этим обновлением:

| Вопрос | Окончательное правило |
| --- | --- |
| Место описаний классов | Между FunctionTable и code_size в 2.0. |
| Запись класса | name:u16, field_count:u16, поля по 5 байтов, method_count:u16, индексы методов u16. |
| Запись типа поля | tag:u8 + class_idx:u16, теги 1/2/3 с FFFF и 4 с конкретным индексом. |
| Вызов метода / инициализации | Обычный CALL; this в slot 0; initializer_idx в файле не нужен. |
| Выделение | 0x40 + class_idx:u16, длина 3, одна новая ссылка. |
| Чтение и запись | 0x41/0x42 + class_idx:u16 + field_idx:u16, длина 5. |
| Версия | 2.0; 1.0 без изменений. |

Равенство объектов, nullable, наследование, виртуальность, флаги val и полные файловые сигнатуры не добавлены. Это не оставшиеся вопросы текущей стыковки и не основания менять описанное поведение. Синтаксис пользовательских конструкторов выбирает команда языка, сохраняя принятую схему инициализации и проверки заполненности.

Готовность теперь зависит от реализации и проверок, а не от отсутствия номеров опкодов или раскладки. Каноническая копия контракта для команды Go&on находится рядом в bytecode-contract.md и не требует перехода в документацию GVM.

## 14. Проверки результата Go&on

### 14.1 Что проверяется по уже определённой модели

| Сценарий | Ожидаемый результат |
| --- | --- |
| Два класса с одинаковыми полями | Разные конкретные типы. |
| Поле с объектным типом | Сохранён конкретный класс поля, а не общий признак «объект». |
| Запись несовместимого значения | Ошибка семантики до записи выходного файла. |
| Одинаковые имена методов у разных владельцев | Разрешение с учётом класса, без глобального смешения. |
| Метод с двумя явными параметрами | This в slot 0, аргументы в slot 1 / 2, param_count=3. |
| Ограничение локальных слотов | This, явные параметры, локальные и временные значения учтены вместе. |
| Подготовка уже вычисленных параметров метода | На вершине this, ниже arg1, arg2 и далее; pop заполняет правильные слоты. |
| Присваивание / аргумент / возврат объекта | Одна и та же ссылочная семантика без неявного копирования экземпляра. |
| Чтение вложенного объектного поля | Тип промежуточного значения остаётся конкретным классом. |
| Метод без результата | Не создаётся фиктивный Unit / NULL; не ставится лишний POP. |
| Неиспользуемый объектный результат | Снимается как одно значение, без ручного удаления объекта. |
| Использование служебного NULL как готового Int / объекта | Не принимается за корректную типизированную инициализацию. |
| Объектное сравнение через старый CMP_EQ | Не объявляется совместимым без определения такой операции. |
| Объектная операция при целевом 1.0 | Нет успешного несовместимого файла или недокументированного хвоста. |

Дополнительно проверить: receiver вычисляется раньше аргументов, каждый ровно один раз; запись поля вычисляет receiver раньше правой части; ALLOC_OBJECT не вызывает инициализацию; CALL инициализатора не оставляет значения, а завершающий LOAD_LOCAL выдаёт одну ссылку; успешные пути инициализации заполняют обязательные поля и не раскрывают недостроенный this.

Для проверки расположения параметров и ссылочной семантики допустимы тесты промежуточной модели. Они подтверждают конкретную часть генерации, но не означают, что уже получен запускаемый объектный `.albc`.

### 14.2 Интеграционные проверки по готовому контракту 2.0

- Создать два экземпляра одного класса и подтвердить независимость их полей.
- Скопировать ссылку и подтвердить видимость изменения через другую ссылку.
- Записать и прочитать поле с конкретным объектным типом.
- Вызвать метод с несколькими явными параметрами и проверить this / аргументы / результат.
- Вернуть объект из завершившейся функции и использовать его в вызывающей.
- Проверить сохранение нужного receiver во время вычисления аргументов согласно принятому порядку языка.
- Проверить реальные выходные байты согласованным загрузчиком, а не только round-trip Go&on.
- Подтвердить корректный отказ при неподдерживаемой операции / профиле без повреждения существующего выходного файла.

Эталонные инструкции, таблицы, смещения и байты основного сценария уже зафиксированы в bytecode-contract.md. Синтаксические фикстуры составляются по реализации языка без изменения контракта. Фактический прогон на GVM и проверка промежуточной модели отмечаются раздельно.

### 14.3 Диагностики

Пользователь должен получать ошибки неизвестного класса, поля или метода, неверного получателя, несовместимого объектного типа, отсутствующего значения и превышения слотов. Сообщение указывает конкретный контекст и доступную позицию исходника.

Отдельно различаются ошибка исходника и отсутствие определённого backend-контракта для объектной операции. Компилятор не должен называть такую операцию успешно скомпилированной только потому, что создал внутренний AST или список произвольных инструкций.

Точные коды диагностик не являются ABI GVM. Их выбирает команда Go&on в существующей системе диагностик и закрепляет тестами.
